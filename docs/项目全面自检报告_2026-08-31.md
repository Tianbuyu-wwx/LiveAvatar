## 三、分维度详细分析

### 3.1 架构设计（8.5/10）

**现状与亮点**

- 分层清晰：`publish（服务）→ pipeline/duplex（编排）→ adapter/runtime（会话中枢）→ pool/voice（资源）→ musetalk/face（推理）`，依赖方向单向向下 [源码]。
- **单一打断权威**：epoch 机制贯穿 push 与 duplex 两条链路（`pipeline.cancel_epoch` / `worker.advance_epoch`），worker 是唯一 epoch 源，publisher 只做过期帧丢弃 [源码]。
- **可插拔发布端**：`PublishSink` 协议下自研 `WebSocketSink`（默认）与 LiveKit `AvatarVideoPublisher` 可切换，`LIVEAVATAR_TRANSPORT=ws|livekit` 过渡开关符合既定迁移约定 [源码]。
- **自研传输协议**：26B 帧头 + MJPEG/region-delta 双编码 + 每帧独立可解码 + 5 档自适应质量状态机，弱网按窗口上报（streak=3）恢复，均为上一轮弱网问题的结构性修复 [源码]。
- **资源治理**：`_common/pool.py` 泛型租约池被 avatar 池与 voice 池复用；`_BoundedQueue` 统一跨线程/跨事件循环通信，已无裸用 `asyncio.Queue` 的跨线程点 [源码]。

**问题与风险**

| 编号 | 级别 | 问题 | 证据 |
|------|------|------|------|
| A1 | P2 | `publish.py` 782 行，承担路由、会话生命周期、编码器工厂、鉴权、配置 5 类职责，是依赖汇聚点（god module 苗头） | [源码] publish.py 全文 |
| A2 | P2 | `duplex.py` 与 `runtime/livekit_runtime.py` 各自重复实现"可选导入 + 辐条组装 + 能力开关"约 50–80 行，语义相同、实现两份 | [源码] duplex.py:51-99 / livekit_runtime.py:46-99 |
| A3 | P2 | LiveKit 过渡代码（video_publisher/livekit_runtime/livekit_adapter/tutor_publisher，约 1,100 行）在 2 个 minor 版本周期后需退役，目前无退役跟踪项 | pyproject coverage omit 清单 [源码] |
| A4 | P3 | `_common/pool.py` 465 行泛型池复杂度偏高（泛型 + 租约 + 再生策略叠加），缺一份内部设计说明 | [源码] |

## 六、结论

项目经 R2（自研传输）与 duplex（全双工星型架构）两轮迭代后，架构与技术自研度显著高于上轮评估，性能指标全面优于预算；**当前短板收敛为三类**：安全细项（反序列化防御、CI 供应链）、可观测性（/metrics/TraceID/性能门禁）、以及 R1 最后一步 GPU 训练。按本计划推进，第 2 周可完成安全与质量补课（M-A），第 8 周达成"自研人脸 + 可观测"（M-B），第 16 周达到生产可用（M-C）。
